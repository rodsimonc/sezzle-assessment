# v1.0.0: Calculator, first release

**Status:** In development
**Target date:** 2026-10-09
**Branch:** main (backend, frontend, evals, docs in one repository)

MAJOR (SemVer): first public release, so there is no earlier contract to break.

This release ships the whole product. A Go service does the arithmetic behind a versioned REST API. A React keypad calculator talks to it. A Docker image runs both. Every acceptance criterion below has a golden case, and every golden case has an executable eval. The eval files were written from this document before the code they test.

## How to read this file

- Each requirement has a **Golden case**: concrete input and the exact expected output. The eval turns it into code.
- **Eval** is the path of the file that checks the requirement. One file per requirement.
- Status boxes stay `[ ]` until the eval passes. Marking `[x]` without a green eval is a process error.
- Values in golden-case tables are what the HTTP API returns. "422 `DIVISION_BY_ZERO`" means status 422 and `code` equal to `DIVISION_BY_ZERO`, with the body shape from `docs/ERROR-CONTRACT.md`.
- Calls are `POST /api/v1/calculations` with `{"operation": ..., "operands": [...]}` unless a row says otherwise.

## Eval conventions

- Runner: Playwright Test, three projects: `api` (no browser), `ui` (Chromium, each eval sets the viewport it needs) and `delivery` (Node scripts and Docker).
- Base URL: `EVAL_BASE_URL`. When it's unset, `evals/lib/server.ts` starts `backend/bin/server` on a free port per worker with `RATE_LIMIT_PER_MINUTE=0`, `LOG_LEVEL=warn` and `STATIC_DIR=frontend/dist`.
- Evals that need a special server configuration (items 2.7, 2.8 CORS part, 2.10) start their own instance. They skip themselves, with a visible reason, when `EVAL_BASE_URL` is set.
- File name: `evals/v1.0.0/<layer>/item-<id>-<slug>.eval.ts`. The `<id>` must match the heading number in this file.
- The top-level `test.describe` title starts with the item id and a space, such as `1.1 Addition`, so `playwright test -g "^1\.1 "` runs one item.
- API and UI evals import `test` and `expect` from `evals/lib/fixtures.ts`, which gives each worker its own server (or the `EVAL_BASE_URL` one). Delivery evals import from `@playwright/test`.
- An eval tests behaviour, not exact strings, except where this file names the exact string (error `detail` text in the OpenAPI examples, UI labels in the UI contract).
- Every eval file contains at least 3 assertions and at least one negative case that would fail if the feature were removed.
- A retired requirement deletes its eval in the same release. No commented-out evals.

## UI contract

The UI evals and the frontend both read this section. If it changes here, it changes in both places.

**Accessible names (exact, case-sensitive).** Every key is a `<button>`. Its accessible name is:

| Key | Name | Visible label |
|-----|------|---------------|
| Digits | `0` to `9` | same |
| Decimal | `Decimal point` | `.` |
| Add / Subtract / Multiply / Divide | `Add`, `Subtract`, `Multiply`, `Divide` | `+`, `-`, `×`, `÷` |
| Power | `Power` | `xʸ` |
| Percent | `Percent` | `%` |
| Square root | `Square root` | `√` |
| Reciprocal | `Reciprocal` | `1/x` |
| Square | `Square` | `x²` |
| Negate | `Negate` | `±` |
| Equals | `Equals` | `=` |
| All clear | `All clear` | `AC` |
| Backspace | `Backspace` | `⌫` |
| Memory | `Memory clear`, `Memory recall`, `Memory add`, `Memory subtract` | `MC`, `MR`, `M+`, `M-` |
| History | `Clear history` | `Clear` |

**Elements the evals look for:**

- `data-testid="display"`: the current number as text. `0` on load. `Error` in the error state.
- `data-testid="expression"`: the pending expression, such as `2 +` or `15 %`. Empty when nothing is pending.
- The display sits inside an element with `role="status"` and `aria-live="polite"`.
- `data-testid="memory-indicator"`: present with the text `M` only while memory is not zero.
- `role="alert"`: appears only while an error is showing and holds the error text.
- `<section aria-label="History">` holding an `<ol>`. Each `<li>` holds one `<button>` whose text is the entry. The empty state text is `No calculations yet.`
- On screens narrower than 768 px the History section sits behind a disclosure button named `History` with `aria-expanded`. At 768 px and wider it's always visible, to the right of the calculator.
- The keypad container has `aria-busy="true"` while a request is in flight.

**Operator glyphs in the expression line and history:** `+`, `-`, `×`, `÷`, `^`, `%`. History entries read like `2 + 3 = 5`, `15 % 200 = 30`, `2 ^ 10 = 1024`, `√(9) = 3`, `1/(4) = 0.25`, `(5)² = 25`.

**Behaviour rules the frontend follows:**

1. Digit entry replaces a lone `0`, blocks extra leading zeros, accepts one decimal point and stops at 15 digits.
2. `Negate` flips the sign of the number on screen by editing the string. It makes no API call. On `0` it does nothing.
3. A binary operator key stores the number on screen as the left operand. Pressing a second operator before typing a new number replaces the first one with no API call.
4. Pressing a binary operator when a left operand, an operator and a new number all exist runs the pending operation first (left to right) and shows the result.
5. `Equals` runs the pending operation. Pressing `Equals` again repeats the last operator with the last right operand against the number on screen.
6. Unary keys (`Square root`, `Reciprocal`, `Square`) act on the number on screen at once and replace it. A pending binary operation stays pending.
7. After a result, a unary key, a memory key or a history click, a digit starts a new number. An operator continues from the number on screen.
8. `Memory add` and `Memory subtract` call the API (`add`, `subtract` with memory first, screen second). `Memory recall` puts the memory value on screen as a finished number. Memory is React state and resets on reload.
9. Any API or network failure shows `Error` on the display and the message in `role="alert"`. In the error state only digits, `Decimal point`, `All clear`, `Backspace` and `Memory clear` act. A digit starts a fresh number and clears the alert.
10. While a request is in flight, key presses are ignored.
11. Error text is the problem `detail` from the API. If there is no response: `Can't reach the calculator service. Check your connection and try again.` If the response isn't Problem Details JSON: `The calculator service returned an unexpected response.`
12. History records each successful `Equals`, chained step and unary key. It skips memory keys and errors. Newest first, capped at 50, stored in `localStorage` under `calculator.history.v1` as a JSON array of `{ "expression": string, "result": string, "timestamp": ISO 8601 }`. Broken or missing storage never crashes the page.
13. Clicking a history entry puts its result on screen as a finished number.
14. The page makes no arithmetic of its own. Every number shown after a computation came back from the API.

#### 2.7 Rate limiting

- **Type:** Feature
- **Repos:** Backend
- **DB migration:** No
- **Status:** [ ] Pending
- **Description:** A per-client token bucket guards `/api/` routes. `RATE_LIMIT_PER_MINUTE` is the refill rate (0 turns the limiter off). `RATE_LIMIT_BURST` is the bucket size. The client key is the remote address, or the first `X-Forwarded-For` entry when `TRUST_PROXY=true`. `/healthz` and static files are exempt.
- **Acceptance criterion:** With `RATE_LIMIT_PER_MINUTE=60` and `RATE_LIMIT_BURST=5`, six quick requests give 200 five times and then 429 `RATE_LIMITED`. The 429 has an integer `Retry-After` header of at least 1, and `retryAfter` in the body equals it. `/healthz` still answers 200 while limited. After waiting `Retry-After` seconds, the next request returns 200. With `TRUST_PROXY=true`, two different `X-Forwarded-For` values have separate buckets. With `TRUST_PROXY` unset, the header is ignored.
- **Golden case:** as in the criterion.
- **Eval:** `evals/v1.0.0/api/item-2.7-rate-limiting.eval.ts`

#### 2.8 Headers, CORS and health

- **Type:** Feature
- **Repos:** Backend
- **DB migration:** No
- **Status:** [ ] Pending
- **Description:** Request ids, security headers, an opt-in CORS allowlist and a health endpoint.
- **Acceptance criterion:**
  - Every response has `X-Request-Id`. With no incoming id it's 32 hex characters. A valid incoming id (`^[A-Za-z0-9._-]{1,64}$`) is echoed. An invalid one (a space, or 65 characters) is replaced. Error bodies carry the same value as `requestId`.
  - Every response has `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and a `Content-Security-Policy` that contains `default-src 'self'` and `frame-ancestors 'none'`. Responses under `/api/` also have `Cache-Control: no-store`.
  - With `CORS_ALLOWED_ORIGINS=https://app.example.com`: a preflight (`OPTIONS /api/v1/calculations` with that `Origin`, `Access-Control-Request-Method: POST`) returns 204 with `Access-Control-Allow-Origin` equal to the origin, `Vary: Origin`, an allowed-methods header containing `POST` and an allowed-headers header containing `Content-Type`. A preflight from `https://evil.example` returns 403 `CORS_ORIGIN_NOT_ALLOWED`. A normal `POST` from `https://evil.example` is served but has no `Access-Control-Allow-Origin`.
  - With `CORS_ALLOWED_ORIGINS` unset, no response has `Access-Control-Allow-Origin`.
  - `GET /healthz` returns 200 and `{"status":"ok","version":"1.0.0"}`.
- **Golden case:** as in the criterion.
- **Eval:** `evals/v1.0.0/api/item-2.8-headers-cors-health.eval.ts`

## Design decisions

- **Stateless backend.** History lives in the browser. The service can restart or run in two copies with no coordination.
- **15 significant digits.** Enough to scrub float noise and to keep integers up to 15 digits exact. The cost: a result between 10^15 and 2^53 loses its last digit. Item 1.11 pins this behaviour and the README lists it under known limits.
- **Two API styles, one service.** The resource endpoint is the canonical one. The per-operation routes are a convenience that calls the same service method, so the two can't drift.
- **Arithmetic stays on the server.** Even `M+` and `M-` call the API. The frontend has no arithmetic to get wrong, and the evals can prove it.
- **400 for shape, 422 for rules.** Taken from the controller block in the reference folder.
- **Titles from a table.** Problem `title` text doesn't depend on the Go standard library's wording.
- **One binary serves everything in Docker.** One port, one health check, no CORS needed.
- **Evals before code.** Items were written as golden cases first. The eval files come from this document, not from the implementation.

## Execution strategy

1. Contract (this file, `specs.md`, `openapi.yaml`, `ERROR-CONTRACT.md`) is committed first.
2. Scaffold: manifests, tooling and dependencies with pinned versions.
3. In parallel: backend, frontend, API evals, UI evals, delivery evals and tools, Docker and CI and docs sources.
4. Integration: build everything, run every check, fix.
5. Review: independent checks of contract fit, security, UI in a real browser, docs from a clean clone, and eval quality.
6. Close: README with real numbers, coverage snapshot, CHANGELOG, tag.
